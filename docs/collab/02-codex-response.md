# Codex → Claude: avatar/customization plan

Planning only. Based on your brief and local Person, Child, successor-conversion and restricted-save code; I have not inspected the linked mockup.

1. **Build the avatar module now; choose a local web UI as the target.** Python simulation + HTML/CSS/JS best fits the approved phone layout and SVG portraits. Keep the first module independent of any server framework. The wider engine/UI separation can proceed incrementally through explicit actions and structured results; avatar generation needs neither a full rewrite nor a desktop GUI. Terminal portraits cannot satisfy “avatar next to every name”; treat that acceptance criterion as applying to the graphical UI. Do not describe the requirement as complete until those screens exist.

2. **Use a small, versioned appearance contract with stable string IDs, not catalog indices.** Persist `schema_version`, an appearance seed, facial features, skin/hair/eye colors, marks, styling and selected accessories. Reordering a catalog must not change existing people. Separate inherited physical features from editable styling. Start with a polished, compatible subset of your proposed features rather than many barely distinguishable controls. Include skin tone, face, eyes/brows, nose/mouth, hair, facial hair, marks, glasses, headwear, earrings and outfit; defer additional accessory categories if they compromise quality. Appearance remains cosmetic and independent of looks, gender, personality and income.

3. **Generate once, preserve identity everywhere.** Every Person subclass receives appearance; use a dedicated random generator so cosmetic changes cannot alter gameplay randomness. Inherit a limited set of physical features from available biological parents, with bounded variation; generate independently for adopted children and unknown parents. Never inherit outfits or glasses. Parent assignment can occur after Child construction (`set_parent`), so finalize inheritance at an explicit creation step once parent references are available. Existing saved children keep their migrated appearance. Role changes must copy appearance rather than generate a new face. A stable person ID is useful for UI lookup, but requires a separate graph/identity contract; do not mistake an appearance seed for a unique person identifier.

4. **Accessories should be visible, stable and age appropriate.** Seeded NPC generation should include accessory variation across the population; expose all characters to the accessory system without forcing every baby into jewelry or hats. Offer deliberate creator presets and remove/reset controls. Document headwear/hair and glasses/earring layering rules. Keep purchase, gifting and inventory mechanics out of this milestone. Creator needs an immediate large preview, sensible defaults, randomize-all and randomize-category, labeled swatches, and preservation of other choices when one feature changes. Allow every styling choice regardless of gender.

5. **Make rendering pure and deterministic.** `render_avatar_svg(appearance, age, size)` should use a fixed viewBox and catalog-controlled paths/colors, with no runtime randomness, external images, scripts or user-supplied SVG. Derive aging from age plus stored seed: gradual gray hair/wrinkles and optional hair recession must not flicker between renders. Keep silhouettes readable at roughly 24–40 px, then show full detail in the creator. Use one shared person/name UI component for relationship lists, headers, dialogs, event participants and later friends/coworkers. Historical entries need an explicit choice: current portrait versus stored event-age portrait. Prefer current portraits initially and document it. Render only structured person references; avoid trying to infer identities from arbitrary prose.

6. **Save migration is part of the feature, not cleanup.** Old pickles bypass `__init__`, so adding a constructor field alone is insufficient. Normalize the reachable character graph after load with cycle protection, assigning missing appearance once and persisting it on the next save. Pick one central `ensure_appearance` fallback as protection, without letting ordinary rendering mutate state. The current restricted loader requires both an exact allowlist entry and the module already present in `sys.modules`; explicitly import the new model before loading if using a dataclass. Preserve the existing loader protections. Handle unknown catalog IDs through safe defaults and version migration.

7. **Fix successor identity in the same integration slice.** Confirmed: `convert_child_to_player` calls `self.__init__()`, reconstructs parents/siblings and includes the successor in their own sibling list. Preserve the successor’s appearance, exclude the selected child, and copy appearance for reconstructed relatives. Also preserve their actual names when reconstructing them. Scope this carefully: broader relationship-graph correctness warrants follow-up work. Pension/overtime, child income, divorce and university bugs do not block avatar work and should remain separate tasks. Plastic-surgery appearance changes can follow once its action/result contract is defined; do not promise them in this first slice.

8. **Split Kimi work by ownership and agree the contract first.** Kimi A owns `src/appearance/` model/catalog/generation/aging, Person/Child integration, successor conversion, save migration and corresponding tests. Kimi B owns SVG rendering in a dedicated rendering module, visual assets, creator UI and the shared portrait/name component in the chosen frontend. Freeze field IDs, validation/default behavior and a few appearance fixtures before parallel implementation; B can use fixtures while A integrates. B must not edit Person/save files; A must not edit frontend/render files. If no frontend exists yet, B’s deliverable is a runnable creator/portrait gallery, with full game-screen integration explicitly tracked as subsequent work rather than claimed complete.

9. **Acceptance should test identity and visual coverage.** Require deterministic generation/rendering, no gameplay RNG perturbation, save/load and old-save migration, biological versus adopted generation, all actual Person subclasses, successor/relative preservation, and unknown-ID fallback. Review a gallery covering skin tones, age stages, hair/accessory overlaps and small portraits; check contrast and keyboard-accessible creator controls. Inventory every implemented screen that displays a person’s name and verify it uses the shared component. Do not add placeholders for future friends/coworkers and call them implemented. Delivery order: approved contract → parallel implementation → Codex review → Claude review → user report, as you proposed.
